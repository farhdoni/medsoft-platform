## Главный вывод

Права нельзя включить одной строкой `router.use('*', requireX)` на каждый
файл — это работает только там, где роутер целиком обслуживает один раздел
(образец — `admins.ts`, см. раздел 1). Как минимум три файла так не устроены:
внутри одного роутера вперемешку лежат маршруты, которым по разделу 3 нужны
разные права. Прежде чем вешать проверки, эти файлы нужно физически
разделить на под-роутеры (или расставлять проверки на каждый маршрут
индивидуально) — это отдельный этап работ, предшествующий включению самого
контроля доступа.

| Файл | Маршрутов | Прав внутри одного файла | Что смешано |
|---|---|---|---|
| `routes/aivita-admin.ts` | 22 | 4 (после сегодняшнего разделения — 8, см. раздел 3) | `users:*` (10), `aivita:doctors_read/manage` (5), `aivita:billing_read/manage` (5), `aivita:content_read/manage` (2, `home-settings`) |
| `routes/admin/users.ts` | 13¹ | 3 (роли, команда, пользователи AIVITA) | `settings:roles_read/manage` (4: 1 чтение + 3 записи), `settings:team_read/manage` (3: 1+2), `users:read/edit/delete` (6: 2 чтения + 4 записи) |
| `routes/clinic-requests.ts` (`clinicAdminRouter`) | 3 | 2 | смонтирован дважды в `index.ts` (`/v1/admin/content` и `/v1/admin/stats`) одним и тем же роутером — `content:clinic_requests_read/manage` (2) и статистика скачиваний, ближе к `main:read` (1: `/stats/downloads`), физически неразделимы по пути монтирования |

¹ Было указано 8 — пересчитано при сегодняшней правке: прошлый grep не ловил
многострочные `router.post(`/`router.put(` без аргумента на той же строке.
Заодно обнаружилось, что корневые маршруты `admin/users.ts` (`GET /`,
`GET /:id`, `PUT /:id`, `POST /:id/block`, `POST /:id/reset-password`,
`DELETE /:id`) читают ту же таблицу `aivitaUsers`, что и `/users/*` в
`aivita-admin.ts` — то есть один и тот же ресурс (пользователи AIVITA)
администрируется из **двух разных файлов**. Не решаю здесь, дублирование
это или разные точки входа с разным назначением — фиксирую как находку для
отдельной проверки, не как часть текущей задачи.

Грубая оценка объёма: **минимум 3 файла, ~9-10 групп прав, ~38 маршрутов**
нужно перегруппировать до того, как это можно закрыть проверками. Это
только то, что попало в разведку верхнего уровня — полная инвентаризация
каждого роутера потребует отдельного, более глубокого прохода и может найти
больше таких файлов.

Отдельно, но дешевле: `admin-partners.ts` (раздел «Партнёры») уже физически
разделён по маршрутам (`POST /`, `PATCH /:code/status` — одна группа;
`POST /:code/issue-key`, `POST /:code/revoke-previous-key` — другая) —
развести `partners:manage`/`partners:issue_key` там можно точечными
проверками на маршрут, без переделки файла. То же верно для большинства
пар «чтение/изменение», разведённых в разделе 3 правкой 2026-09-01 — там,
где GET и мутации уже лежат на разных путях в существующем коде, разнести
права дёшево; тяжёлые случаи — только три файла в таблице выше.

## 1. Три существующих словаря ролей

### 1.1 `admin_role` — enum в Postgres (`packages/db/src/schema/admins.ts:3`)

```
'superadmin' | 'admin' | 'viewer'
```

Единственное поле, которое реально попадает в JWT (`payload.role`) и в
`c.get('adminRole')`. Используется в 9 местах:

| Файл | Что делает |
|---|---|
| `middleware/auth.ts:47` | `requireSuperadmin` — `adminRole !== 'superadmin'` |
| `middleware/auth.ts:70` | `requireOperator` — сверяет с `OPERATOR_ROLES` (см. 1.2) |
| `routes/index.ts:295,301` | сидер супер-админа при старте |
| `admin/src/.../admins/page.tsx:41,71` | UI: бейдж роли, доступность действий |
| `admin/src/.../aivita/support/page.tsx:704` | UI: кнопка снятия PII-блока только superadmin |
| `admin/src/.../settings/team/page.tsx:67` | UI: спецобработка `role === 'admin'` |
| `admin/src/components/layout/sidebar.tsx:165` | UI: пункт «Админы» только superadmin |

### 1.2 `OPERATOR_ROLES` — хардкод-массив (`middleware/auth.ts:54`)

```ts
const OPERATOR_ROLES = ['superadmin', 'admin', 'moderator', 'support'];
```

Используется в `requireOperator` (2 проверки в том же файле, единственный
потребитель — `aivita-admin-support.ts`, кабинет поддержки). Два из четырёх
значений (`moderator`, `support`) **не существуют** в enum 1.1 — это
самостоятельный, третий словарь имён, который пересекается с 1.1 только
частично.

**Решение (2026-09-01): `admin` убирается из `OPERATOR_ROLES`.** В целевой
модели Директор не входит в `aivita:support` (раздел 6) — сегодня
`OPERATOR_ROLES` даёт роли `admin` (=Директор) доступ к тикетам поддержки
как побочный эффект того, что `admin` в этом массиве был нужен для чего-то
другого исторически. Живых аккаунтов с ролью `admin` на проде — 0 (раздел
7), сужать доступ не у кого — это финальное целевое состояние, не
переходный компромисс, который решили не откладывать: переходные
исключения такого рода имеют свойство становиться постоянными. Целевой
массив: `['superadmin', 'moderator', 'support']`. Это правка кода
(`middleware/auth.ts:54`) — сама правка не входит в текущую задачу
(документ без кода), но решение по содержимому массива принято и
зафиксировано здесь, а не оставлено открытым вопросом.

### 1.3 `admin_roles.name` — таблица на проде, редактируется из панели

```sql
select id, name, display_name from admin_roles order by id;
```
```
1  superadmin   Супер-администратор
2  admin        Администратор
3  moderator    Модератор
4  support      Поддержка
5  marketing    Маркетинг
6  finance      Финансы
```

Свободный текст — панель (`settings/roles/page.tsx`) не ограничивает `name`
ничем. Используется в 2 файлах: `middleware/auth.ts` (только `.name`, для
джойна в `requireOperator`) и `routes/admin/users.ts` (CRUD + отдача списка).
`admin_user_roles` (таблица назначений роль→пользователь) **пуста** — 0
строк на проде. Итог: 6 ролей заведены, но не привязаны ни к одному живому
админу; вся реальная авторизация сегодня идёт через enum 1.1.

## 3. Карта ~205 маршрутов и предлагаемые права

205 — это реальный админский периметр: `/v1/admin/*`, `/v1/admins`,
`/v1/aivita-admin*`, админ-часть `clinic-requests.ts`. Не включает публичный

## 4. Медицинские данные, персональные данные, согласия, выписки — третий уровень

Проверено: среди всех 205 админских маршрутов нет ни одного, читающего
диагнозы, назначения, согласия (`consents`) или выписки (`discharge-
documents`) напрямую. Единственный след — `aivita-admin-support.ts:316-318`
читает `medicalCards.cardCode` (код карты, не содержимое) для карточки
пользователя в поддержке.

Настоящие маршруты с медданными (`/v1/aivita/consents`, `/v1/aivita/medical`,
`/v1/aivita/doctor/prescriptions`, `/ecosystem/v1/discharge-documents`)
принадлежат периметру пациента/врача, не админки, и защищены отдельной
авторизацией — они не входят в 205.

Третий уровень:

- **`pii:reveal`** — право видеть персональные данные пользователя вне
  обезличенной карточки поддержки (полный профиль, разблокировка PII).
  Перенесено сюда правкой 2026-09-01 из раздела 3, где было заведено как
  `aivita:support_pii` (право на раздел «Поддержка») — по факту это не
  право на раздел, а самостоятельное право на просмотр личных данных,
  которое концептуально стоит рядом с медицинскими, а не с тикетами
  поддержки. **Каждое раскрытие обязано писаться в журнал с причиной** —
  это требование к аудиту (кто, когда, какую карточку, зачем), а не только
  флаг доступа; сегодня такого журнала в коде нет — фиксирую как будущее
  требование к реализации, не описание текущего поведения.
- `medical:read_phi` — чтение диагнозов/назначений/содержимого согласий, если
  такой маршрут появится в админке (напр. разбор жалобы с доступом к карте).
- `medical:manage_phi` — запись/аннулирование согласий, работа с выписками от
  имени администратора.

`medical:read_phi` и `medical:manage_phi` не назначаются ни одной роли в
разделе 6 — держатся как расширение на будущее. `pii:reveal`, в отличие от
них, уже используется (Оператор поддержки (старший)) — это не новая
функция, а старая (`aivita:support_pii`), просто теперь явно оформлена как
право третьего уровня, а не спрятана внутри раздела «Поддержка».

не найден. Спроектирован по названию роли и структуре панели, затем дважды
скорректирован владельцем продукта 2026-09-01.*

|---|---|

| **Кадры** | `settings:team_read`, `settings:team_manage`, `main:read` |

**Бухгалтер — видит ставки, не меняет (2026-09-01).** `finance:settings_read`
добавлено: комиссии — то, с чем бухгалтер работает каждый день, и не видеть
текущие ставки при этом было странно. Менять их по-прежнему нельзя —
`finance:settings_manage` остаётся у Директора и Супер-админа.

**Маркетолог — звёздочки развёрнуты в список (2026-09-01).**
`marketing:*`/`content:*` были единственным местом в разделе 6, где право
выдавалось оптом, а не поимённо — после разведения пар (раздел 3) звёздочка
стала означать «и чтение, и запись» без явного перечисления, то есть
единственным исключением из общего правила. Развёрнуто в явный список.
Побочный эффект вскрылся при развороте: `content:*` через общий префикс
`content:` заодно захватывал `content:clinic_requests_read/manage` —
Маркетологу это не нужно (это инструмент Продавца MedSoft), в явном списке
его больше нет. Ровно та находка, ради которой просили разворачивать:
звёздочка расширяла доступ незаметно.

**`finance:prices_manage` — маркетинг, не бухгалтерия.** Цена на продукт
(сколько стоит подписка) — решение о позиционировании, которое принимает
владелец продукта; движение уже заплаченных денег (возврат, выплата,
промокод — `finance:edit`) — бухгалтерская операция. Разные по природе
вещи, которые без разведения легли бы в одно право. Выдано Маркетологу и
Директору, не выдано Бухгалтеру (видит ставки через `finance:settings_read`,
но не устанавливает розничную цену продукта). Что физически покрывает
право сегодня и чего не покрывает («консультация») — раздел 3, сноска⁴.

**Директор — правка 2026-09-01 (доктора/биллинг).** Разведение
`aivita:doctors_manage`/`aivita:billing` на `_read`/`_manage` (раздел 3)
сделано ровно ради этой роли: раньше «видит всё, меняет мало» для этих
двух разделов было физически невыразимо (одно право на чтение и запись
сразу), поэтому в прошлой версии документа Директор терял оба раздела
целиком. Сейчас — читает оба, не редактирует ни один. Старый флаг под этой
таблицей снят как решённый.

**Директор и поддержка — решено, не открытый вопрос.** `aivita:support` в
списке Директора нет, и это не временное сужение: `OPERATOR_ROLES` в коде
целевого состояния не содержит `admin` (раздел 1.2). Живых Директоров с
доступом к тикетам сегодня 0 — сужать некого, откладывать не имеет смысла.

**Кадры — почему всего два права, это не недосмотр.** Роль выглядит бедной,
потому что кадровый раздел панели пока не построен: сотрудники, кадровые
документы, смены — сегодня это только в ТЗ, не в коде. `settings:team_*`
(панель «Команда» — учётные записи персонала MedSoft) и `main:read` — это
всё, что для кадровой функции существует физически. Как только появится
кадровый модуль (карточки сотрудников, документы, графики смен) —
у роли Кадры появятся новые права под него; текущий список — не финальный
потолок роли, а снимок того, что есть в коде сегодня. Записано явно, чтобы
через месяц это не прочитали как «роль забыли наполнить».

## 8. Где новый словарь НЕ ложится без переделки

Это важнее совпадений — фиксирую прямо. Разделение роутеров на несколько
разных прав вынесено наверх, в «Главный вывод» — это самая крупная и самая
важная из этих несостыковок, отдельный этап работ. Ниже — остальное:

1. **`admin_user_roles` пуста.** Новая модель предполагает реальное
   назначение роли на пользователя через эту таблицу — сегодня её никто не
   заполняет, миграции данных для существующих 2 аккаунтов нет.

2. **`admin_roles.permissions` — несовместимый по форме набор.** 13
   косметических флагов (раздел 2) придётся полностью заменить на 37+3
   права из разделов 3-4, а не расширить — старые 6 строк в этой таблице
   не мигрируют автоматически, значения нужно переписывать заново под новую
   схему ключей.

3. **`platform-settings.ts` только что закрыт `requireSuperadmin` напрямую**
   (правка этой недели, вне текущей задачи) — жёстко, не через право.
   Целевая модель хочет `finance:settings_manage`, доступное и Директору;
   Бухгалтер его не получил (раздел 6) — значит сегодня это право реально
   нужно только Директору и Супер-админу, а точку `requireSuperadmin`
   всё равно придётся переоткрывать заново под новый механизм, а не
   оставлять как есть.

4. **`OPERATOR_ROLES` требует правки кода**, не только документа —
   `middleware/auth.ts:54`, снять `'admin'` из массива (решение см. раздел
   1.2). Не входит в текущую задачу (документ без кода), но без этой
   правки Директор по факту сохранит доступ к тикетам поддержки в обход
   раздела 6.

5. **Дублирование `aivitaUsers` CRUD в двух файлах** (`admin/users.ts` и
   `aivita-admin.ts`, см. «Главный вывод», сноска ¹) — один и тот же ресурс
   (пользователи AIVITA), две точки входа, и по этой разведке не видно,
   какая из них живая, а какая — задублированный или мёртвый код на боевом
   API. Это находка за рамками прав: пока оба файла попадают под одни и те
   же права `users:read/edit/delete`, поведение снаружи не меняется — но
   вопрос «что из двух реально используется» требует отдельной, не ролевой
   разведки, и его нельзя потерять. Пока права не мешают — оба файла под
   одним и тем же гейтом дают одинаковый результат снаружи; но именно
   поэтому `admin/users.ts` нельзя закрыть одной строкой на весь роутер.

6. **То же дублирование, вторым экземпляром: цены `subscriptionPlans`**
   (раздел 3, сноска⁴) — `admin/finance.ts` (`PATCH /plans/:id`,
   `finance:prices_manage`) и `aivita-admin.ts` (`POST/PATCH /billing/plans`,
   `aivita:billing_manage`) пишут одну и ту же таблицу из двух разных
   файлов под разными правами. Сегодня безопасно — `aivita:billing_manage`
   есть только у Супер-админа — но это тот же класс проблемы, что и пункт
   5, найденный тем же способом (построчная проверка при разведении прав) в
   другом месте кода. Оба дублирования стоит разобрать в одном заходе на
   этапе разделения роутеров, а не по отдельности.
