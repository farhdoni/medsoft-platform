# Эталон схемы прода

Отпечаток боевой базы (`medsoft`, контейнер `t6j97mmeou41tcsuv2h3qhgj`), от которого
идёт следующая сверка. Обновляется только после деплоя, изменившего схему, — и
только вместе с объяснением, почему изменение ожидаемо.

## Правило: применённые миграции не редактируются

Мина 0025 (см. её шапку и 0042) случилась ровно из-за нарушения этого правила:
коммит переписал уже применённую миграцию вместо нового файла, и `CREATE TABLE
IF NOT EXISTS` сделал правку невидимой для баз, где 0025 уже отработала.

Единственное разрешённое исключение — комментарии. Правка КОММЕНТАРИЯ в уже
применённой миграции допустима, если тело SQL (всё, что не начинается с `--`
или не находится внутри `/* … */`) не меняется ни на символ; каждая такая
правка фиксируется здесь: файл, дата, что добавлено, почему тело не тронуто.
Любое изменение тела SQL — включая типы, значения по умолчанию, порядок
statement-breakpoint — идёт только новым файлом, как 0042.

* **30.08** — `0025_av_chat_messaging.sql`: добавлена шапка-предупреждение
  (12 строк, все `--`) о мине с наивными timestamp-колонками и ссылка на 0042.
  Тело SQL не тронуто — правку можно проверить `git diff`: только добавленные
  строки, ни одной удалённой или изменённой. Первый случай применения этого
  правила.

### Как снять тот же отпечаток

Считается по колонкам с типами, индексам и ограничениям схемы `public`.
Порядок фиксирован сортировкой, иначе md5 плавал бы между запусками.

```sql
select md5(string_agg(x, '|' order by x)) as schema_md5
from (
  select table_name || '.' || column_name || ':' || data_type as x
    from information_schema.columns where table_schema = 'public'
  union all select indexname from pg_indexes where schemaname = 'public'
  union all select conname from pg_constraint
) s;
```

Прогонять через stdin — кавычки не переживают цепочку ssh → docker exec → sh -c:

```bash
cat snap.sql | ssh aivita-vps "docker exec -i t6j97mmeou41tcsuv2h3qhgj \
  sh -lc 'psql -U \$POSTGRES_USER -d \$POSTGRES_DB -At -f -'"
```

**Ловушка методики, уже дважды наступали.** `select conname from pg_constraint`
в этой формуле — **без фильтра по схеме**, специально: constraint'ы не всегда
несут «свою» схему в `pg_constraint` так же прямолинейно, как таблицы и
индексы. Если добавить `join pg_namespace ... where nspname = 'public'» "для
единообразия" с двумя другими подзапросами — счётчик ограничений упадёт с
**428 до 316**, и это выглядит один в один как пропажа ~112 constraint'ов,
хотя на самом деле ничего не терялось. Разбирались с этим 2026-09-01 и
2026-09-02 — оба раза заново. Прежде чем объявлять расхождение реальным —
перепроверь формулу дословно из этого файла, а не по памяти.

## Известное принятое отклонение

`ai_usage_logs.created_at` объявлена в drizzle наивной (`timestamp`, без
`withTimezone`), а фактически на проде и на чистой базе — `timestamptz`.
Направление безопасное (данные не теряют информацию о зоне), обнаружено при
аудите 2026-08-30 перед миграцией 0042 и оставлено как есть: чинить нечего,
исправление наивного объявления — отдельная задача, не блокирует 0042.
Формула md5 сверяет `data_type`, а не факт совпадения с drizzle, так что эта
колонка и так не мешает сходимости отпечатка — фиксируется здесь, чтобы при
следующей сверке кто-то не начал искать в ней регрессию.

## 0042 — догоняющая, timestamptz для AV Chat (не деплой, локальный ремонт)

`0042_avchat_timestamptz_catchup.sql` приводит девять временных колонок AV
Chat (см. файл миграции) к `timestamptz(3)`, если они наивные. На проде и на
любой чистой базе, поднятой миграциями с нуля, все девять уже `timestamptz` —
DO-блок логирует `SKIP … - already "timestamp with time zone"` по каждой и
завершается `altered=0`. Отпечаток схемы не меняется: подтверждено локально
2026-08-30 — md5 базы `aivita-postgres-local` (уже приведённой к форме прода)
до и после прогона 0042 совпал бит в бит (`af02ce66b17c23cfceafd4859428c0b0`).

Затрагивает только базы, поднятые между `1167fc7` и `c979aba` (см.
предупреждение в шапке 0025) — то есть рабочие машины, не прод. На проде эта
миграция — чистая формальность, доводящая журнал миграций до состояния
фактической схемы.

### Волна 1 → `cd6b6edd…` (1180 / 296 / 412 / 106)

До неё было `a2ae8e72ae9cf29a866183cf4cf51d0c` — 1180 / 271 / 378 / 106.

Деплой `45810fc` добавил **58 объектов**: 31 внешний ключ, 23 индекса и 2
уникальных ограничения. Колонки, таблицы и данные не менялись; не исчезло
ничего.

Причина не в новом коде, а в старом расхождении. `0002_bent_clint_barton.sql`
не идемпотентна: на строке 270 стоит `ALTER TABLE "admin_users" ADD COLUMN
"password_hash"` без `IF NOT EXISTS`, и на проде она когда-то оборвалась там,
потеряв весь хвост файла — как раз эти ключи и индексы. Миграция 0039
повторяет хвост идемпотентно и восстановила их.

Проверять изменение стоит по трём признакам сразу, а не по одному md5:

* **исчезло 0 объектов** — изменение аддитивное;
* **все 31 FK встали** — Postgres проверяет целостность при создании, значит
  висячих ссылок в данных не было;
* **оба UNIQUE встали** — дублей не было.

Побочный эффект принят осознанно: теперь эти ключи будут отбивать запись
висячих ссылок, которая раньше проходила молча.

## Сверка при следующем деплое

Снимать отпечаток ДО и ПОСЛЕ. Расхождение — повод остановиться и разобрать, а
не чинить на ходу: список изменившихся объектов удобно получать сравнением с
дампом, снятым перед деплоем.

```bash
docker exec -i t6j97mmeou41tcsuv2h3qhgj pg_restore -l < backup.dump \
  | grep -E " (INDEX|FK CONSTRAINT|CONSTRAINT) " | awk '{print $(NF-1)}' | sort -u
```

У этого сравнения есть известное ложное срабатывание. CHECK-ограничения,
объявленные ВНУТРИ `CREATE TABLE`, не попадают в TOC дампа отдельными
записями — в списке «до» их нет, и после деплоя они выглядят новыми. На волне 2
так всплыл `mood_logs_mood_check`: таблица существовала с 0018, ограничение
объявлено там же инлайн, и `CREATE TABLE IF NOT EXISTS` на этом деплое был
no-op, то есть создать его сейчас было нечем.

Проверять такие находки арифметикой, а не глазами: если счётчик ограничений
сошёлся с тем, что дают сами миграции, лишнего не появилось. На волне 2 было
ровно +15 — 4 PK, 1 UNIQUE, 2 CHECK и 8 внешних ключей; будь `mood_logs_mood_check`
новым, стало бы 16.
